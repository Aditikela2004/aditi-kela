HelpDesk

A service request prototype for a fictional 75-person company. Users submit a request, it goes to the responsible team, and its status stays visible. It uses sample data and has no real users.

My role
I defined the workflow, requirements and delivery plan, and tested the request process with sample data.
Context
Independent project, built with AI assistance. Fictional company and sample data only.
Status
Deployed live prototype. Not a production system.
Planned in
Notion, Jira, Confluence and monday.com
Open the live prototype View the code on GitHub

Problem and user

Employees at the fictional company ask IT, Facilities and HR for help by email and chat. Requests arrive incomplete, nobody knows who owns them, people chase for updates, and department heads cannot see workload. The users are employees who want to ask once and know what happens next, and department owners who need to see what is waiting and who has it.

Key decisions

  • Hold version 1 to the core flow. Sign-in, a shared database, notifications, file uploads and SLA rules were left out. That kept the first release small enough to test request creation and ownership properly.
  • Require an owner before work starts. A request cannot move to In progress without an owner, so work never starts unassigned.
  • Define the metrics on the page. The resolved share is a count of the current list. It is not SLA compliance, and the page says so.

What the prototype does

  • A validated request form, so requests arrive complete.
  • Routing by department, with an owner chosen from that department's team, or an Unassigned state.
  • Three statuses and a dated history of every owner and status change.
  • An overview, request list and analytics view that read from one set of records, with search, filters and CSV export.

Evidence and results

  • Automated unit, static and browser checks cover each of the ten written requirements. The browser checks include the form, keyboard use and focus, a phone-width screen and a storage failure.
  • The analytics view uses simulated events. It shows that tracking is in place, not how people behave.

Limitations and next step

  • No real users have used it, so there is no claim about time saved or adoption.
  • Records live in the browser. Owners and filters are labels, not permissions, and there is no sign-in, shared storage or notifications.
  • The ten manual acceptance scripts have not been run by a person. Accessibility conformance and browsers other than Chromium have not been tested.
  • Next step: run the written usability study with employees from one department and fix what they trip on.

Artifacts

  • Requirements traceability (CSV): each requirement linked to its backlog items, tests and release decision.
  • QA evidence and known gaps: what was tested, what was not, and the release recommendation.
